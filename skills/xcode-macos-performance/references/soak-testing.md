# Soak and load tests on macOS

A soak test runs a realistic scenario for a long time and checks that memory and CPU
reach a **plateau**. It finds slow leaks, abandoned memory and idle cost that short
performance tests miss — essential for menu bar apps, agents, document apps and anything
users leave open for days. A load test is the same procedure with a scaled-up data set
(10× the files, rows or items a heavy user has).

## Procedure

1. **Fixture** — Release build, development-signed (so tools can attach), fixed data set
   generated by a script, same Mac, power state noted (plugged in / battery), no
   debugger. Drive the scenario either with an XCUITest loop or with an app-internal
   soak mode behind a launch argument (e.g. `-soakMode YES`) that repeats the workflow.
   Compile the soak mode only into internal builds.
2. **Warm-up** — run the scenario once before measuring (caches, lazy initialisation),
   like XCTest discarding the first iteration.
3. **Mark iterations** — emit an `OSSignposter` event per iteration so footprint samples
   and traces can be lined up with the workload.
4. **Sample** — footprint every 10 s for 30–60 min; CPU/idle wakeups in parallel with
   `top -l … -stats pid,cpu,mem,power,idlew` (`energy-background.md`).
5. **Snapshot diff** — memory graph after warm-up and at the end; diff heap and leaks;
   check fragmentation with `vmmap -summary` (`% FRAG` ≤ ~25 %).
6. **Evaluate** — fit a line through the footprint after warm-up. A flat line (± noise)
   is a plateau; a steady slope or a staircase (each iteration leaves a step) is
   persistent growth. Separate transient peaks (fine if they return) from growth.
7. **Gate** — fail on new leaks (`leaks` exit code 1) or slope above the budget
   (e.g. > 5 MB/hour). Keep `soak.json`, memgraphs and the summary as artifacts next to
   the commit or CI run.
8. **Idle check** — after the scenario leave the app untouched for 5 minutes: CPU ≈ 0,
   idle wakeups ≲ 1/s, no "Preventing Sleep" unless intended.

## Scripts

`scripts/soak.sh` automates steps 2, 4–7 for an app executable:

```sh
scripts/soak.sh -a /path/App.app/Contents/MacOS/App -d 1800 -i 10 -w 60 \
  -o build/soak -m 5 -- -soakMode YES
```

- Launches the executable directly (not via `open`, so LaunchServices can't start
  another installed copy), waits for the warm-up, writes `pre.memgraph`, samples with
  `footprint --sample … -j soak.json`, writes `post.memgraph`, then quits the app.
- Runs `leaks` on both graphs (exit code = gate), `leaks post -diffFrom=pre`
  (`leaks-new.txt`), `heap post -diffFrom=pre -sortBySize` (`heap-diff.txt`) and
  `vmmap -summary post` (`vmmap-summary.txt`).
- Calls `scripts/analyze_soak.py` (Python 3 standard library, run with `python3 -I`):
  least-squares slope in MB/hour, first/last/peak footprint; exit 1 above
  `--max-mb-per-hour`. Options: `--warmup-samples N`, `--process <name|pid>`.
- Exit code: 0 ok, 1 leaks or growth above budget, 2 tool error.

The footprint JSON has `samples[]`, each with `start_time.wall_time_s` and
`processes[].footprint` in bytes (`"unit": "byte"`, `"bytes per unit": 1`).

Verified on macOS 27.2 / Xcode 27.1: the JSON shape against a live shell process, the
analyzer on flat, too-short and growing inputs, and a full `soak.sh` run against a small
test binary that leaks on purpose (leaks exit 1, positive slope, exit 1).
**Not verified:** a full run against a sandboxed, signed `.app` — attaching may require
the development-signed build described above; a GUI app may need its windows driven by
the soak mode or a UI test.

Notes:

- `leaks <pid> -outputGraph file` only writes the graph and exits 0 — the leak scan runs
  on the file (`leaks file.memgraph`).
- `footprint` for processes of other users needs root — ask before using `sudo`.
- Set `MallocStackLogging=lite` in the app's environment if the memgraphs should contain
  allocation stacks (larger files, slower app).

## Load scenarios worth having

- Largest realistic data set × the most expensive workflow (scan, import, export,
  search).
- Repeated open/close of windows, sheets and the menu bar extra (leaked views and
  observers show up here).
- Long idle with the app in the background or the menu closed.
- Low free memory: run alongside a memory-heavy app; macOS swaps instead of killing, so
  look at responsiveness (hangs) and footprint, not crashes.
